# 一晚上，做进一个已经有 5 个玩家的赛道

> build log，2026-11-10。项目：[decision-card-first](https://github.com/ERun-3/decision-card-first)。

## 起点

朋友在微信里说：「其实应该开发一个 skill——做任何项目前默认先调研有没有类似的软件或 GitHub 项目，有就直接用或者抄代码。」另一个人回：「理想很美好，但是现实不太行。」

我们没有站队，而是现场跑数据。拿我自己真实做过的项目当案例，用 GitHub API 和网页搜索各查一遍：调研本身几秒钟、成本几乎为零；「直接抄」多数不成立（无许可证的项目法律上默认保留所有权利）；「默认触发」在架构上做不到——写在技能正文里是鸡生蛋，正文只有被触发后才加载。那张「现实不太行」的反对票，一半对一半错，错的half后来被我们修好了。

## 一晚上迭代了三版

**v1 当晚就翻车**：实测中 Agent 边调研边装依赖，被手动叫停。原因不是模型不听话，是我们的文档从没写过「输出报告后必须停下」。

**v2 加了硬闸门**：决策卡是本轮唯一交付物，输出后不写代码、不装依赖、不提 PR。修复后同需求重测：21 次工具调用全部只读，出完卡停住，还从候选库的源码里挖出「Windows 没有字体路径、中文必然退化成位图」这个坑。

**v1.1 跨平台实测**：把包丢给另外两个 AI 平台（DSH、ZCode）真装真用。安装自举 3/3 通过——每个安装者都正确找到本平台的技能目录和全局规则文件。最有意思的对照组：给 DSH 发「不要调研直接写」，它一口气写了 **940 行**自研渲染引擎；而调研后的方案约 150 行。940 行就是「重复造轮子」的实测尺寸。

## 中途翻的车（都留了记录）

- **评分表泄漏**：测试材料被放在和被测包同一个目录里，被测 Agent 把评分标准读了——等于开卷考，那轮数据作废。
- **竞品只找到 2/5**：发布前用这个 Skill 查自己（dogfooding），找到 2 个同类就下了「没有正面撞车」的结论。后来发现 GitHub 的 star 排序会把 0★ 新项目埋掉、检索词族没覆盖对方的命名语言——又捞出 3 个，其中一个和我们近同名。**改名，并把这两个盲区修进了技能本身。**
- **同步丢功能**：多平台各自持有副本，一次同步差点把 GITHUB_TOKEN 支持覆盖掉，靠 MD5 比对才抓住。

## 赛道与差异

这个赛道现在至少 5 个玩家。最强的竞品（GitHub Community Spain 出品）调研做得极细：需求框架、分级尽调、证据手册、打分矩阵。但把 5 家摆在一起，有个缺口没人补：**出了报告之后，没有任何一家让 Agent 真的停下来等用户确认**——它们给你专业分析，然后按自己的判断继续干。我们把决定权还给用户，并把这件事做成机制：文档级闸门 + 可选的 hook 硬保证 + 安装时自举注册。

## 数字

调研轮实测：21 次只读调用，output 5,025 tokens；技能注入占单轮上下文 3.9%。我们不宣称省首轮 token——调研本身是净增加成本，省的是返工：一次「方案错了但依赖已经装完」的返工就是几十万到上百万 input tokens 的量级，而那 940 行的对照组证明这个返工不是假设。
